  C'EST QUOI CE PROJET EN 2 PHRASES ?
  ─────────────────────────────────────
  On a des simulations physiques (FEM = Éléments Finis) qui calculent la
  déformation et la contrainte dans une plaque métallique sous traction.
  Ces simulations sont LENTES. On entraîne un modèle ML (LightGBM) pour
  les REMPLACER en prédisant instantanément les mêmes résultats.

  LES 2 CHOSES QUE LE MODÈLE PRÉDIT :
  ──────────────────────────────────────
  ┌─────────────────────────────────────────────────────────────────────┐
  │  max_displacement_m   → De combien la plaque se déforme (en mètres) │
  │  max_von_mises_pa     → La contrainte maximale dans le matériau (Pa) │
  └─────────────────────────────────────────────────────────────────────┘

  LES 3 TYPES DE PLAQUES SIMULÉES :
  ───────────────────────────────────
  ┌──────────────────────┬─────────────────────┬────────────────────────┐
  │   with_hole          │   without_hole      │   with_hole_moving     │
  │                      │                     │                        │
  │  ┌──────────────┐   │  ┌──────────────┐  │  ┌──────────────┐      │
  │  │    ┌──┐      │   │  │              │  │  │  ┌──┐         │      │
  │  │    │  │      │   │  │              │  │  │  │  │ ← bouge │      │
  │  │    └──┘      │ → │  │   (pleine)   │  │  │  └──┘         │      │
  │  │              │   │  │              │  │  │                │      │
  │  └──────────────┘   │  └──────────────┘  │  └──────────────┘      │
  │  Trou centré fixe    │  Pas de trou       │  Trou à position libre  │
  └──────────────────────┴─────────────────────┴────────────────────────┘

────────────────────────────────────────────────────────────────────────────────
  PROCESSING — TRANSFORMATION DES DONNÉES (src/processing/)
────────────────────────────────────────────────────────────────────────────────

  POURQUOI "FEATURE ENGINEERING" ?
  ┌─────────────────────────────────────────────────────────────────────┐
  │  Les données brutes : largeur, hauteur, diamètre du trou, force...  │
  │  Le ML a besoin de PLUS : des indicateurs physiques calculés !       │
  │                                                                      │
  │  Ex: La formule de Peterson donne le facteur de concentration        │
  │  de contrainte Kt. Le modèle apprend mieux avec Kt qu'avec juste    │
  │  le diamètre du trou.                                               │
  └─────────────────────────────────────────────────────────────────────┘

┌──────────────────────────┬──────────────────────────────────────────────────┐
│ Fichier                  │ Rôle détaillé                                    │
├──────────────────────────┼──────────────────────────────────────────────────┤
│ src/processing/          │ CRÉÉ LES 42 FEATURES PHYSIQUES :                 │
│   build_features.py      │                                                  │
│                          │  Catégorie 1 — Géométrie de base (de la plaque) │
│                          │   width_m, height_m, thickness_m, hole_d_m...   │
│                          │                                                  │
│                          │  Catégorie 2 — Physique (formules de mécanique) │
│                          │   Kt_theory   → concentrateur de contrainte      │
│                          │                 (formule Peterson)               │
│                          │   sigma_net   → contrainte nette = F / (A-trou) │
│                          │   epsilon     → déformation théorique            │
│                          │   delta_theory→ déplacement théorique            │
│                          │   ligament    → matière restante autour du trou  │
│                          │   eccentricity→ à quel point le trou est décentré│
│                          │                                                  │
│                          │  Catégorie 3 — Transformations log-espace        │
│                          │   log(largeur), log(force), log(Kt)...           │
│                          │   (aide le modèle avec les grandes plages        │
│                          │    de valeurs)                                   │
│                          │                                                  │
│                          │  SPLIT DES DONNÉES (sans fuite d'info !) :      │
│                          │  ┌─────────────────────────────────────────┐    │
│                          │  │  Hash du simulation_id → % déterministe │    │
│                          │  │  0-70%  → train.parquet                 │    │
│                          │  │  70-85% → val.parquet                   │    │
│                          │  │  85-100%→ test.parquet                  │    │
│                          │  └─────────────────────────────────────────┘    │
│                          │  Même résultat à chaque exécution (reproductible)│
├──────────────────────────┼──────────────────────────────────────────────────┤
│ src/processing/          │ Vérifie la QUALITÉ des données avant de les       │
│   validate.py            │ utiliser. Rejette les données corrompues.         │
│                          │                                                  │
│                          │  Ce qui est vérifié :                            │
│                          │  ✓ Colonnes obligatoires présentes (16 champs)   │
│                          │  ✓ Pas de valeurs nulles/NaN                     │
│                          │  ✓ Plages numériques réalistes (ex: force > 0)  │
│                          │  ✓ Cohérence géométrique (trou < plaque)         │
│                          │  ✓ simulation_id unique (pas de doublons)        │
└──────────────────────────┴──────────────────────────────────────────────────┘

│                          │  (arbres de décision empilés, très performant     │
│                          │   sur données tabulaires)                         │
│                          │                                                  │

│                          │  DEUX MODÈLES entraînés (un par cible) :          │

│                          │                                                  │
│                          │  TECHNIQUES ANTI-FUITE DE DONNÉES :              │
│                          │  L'encodage catégoriel est appris SEULEMENT       │
│                          │  sur train, puis appliqué à val/test.             │
│                          │  (bug corrigé : était fait sur tout avant)        │
│                          │                                                  │
│                          │  RÉSULTATS ATTENDUS :                            │
│                          │   R²(log) > 0.99  → excellente précision         │

├──────────────────────────┼──────────────────────────────────────────────────┤

│                          │  RandomForest = forêt d'arbres de décision       │

│                          │  HIÉRARCHIE :                                    │

────────────────────────────────────────────────────────────────────────────────
  API — SERVEUR DE PRÉDICTIONS (src/api/)
────────────────────────────────────────────────────────────────────────────────

  L'API permet à n'importe quel programme (ou humain) d'obtenir des
  prédictions en envoyant une requête HTTP — comme un formulaire web.

  COMMENT FONCTIONNE L'API ?
  ┌─────────────────────────────────────────────────────────────────────┐
  │  Client (dashboard ou curl)                                         │
  │       │                                                             │
  │       │  POST /predict                                              │
  │       │  { "width_m": 0.1, "height_m": 0.2, "force_n": 50000 }    │
  │       ↓                                                             │
  │  FastAPI (port 8000)                                                │
  │       │                                                             │
  │       │  1. Vérifie le mot de passe (Basic Auth)                   │
  │       │  2. Valide les données (Pydantic)                           │
  │       │  3. Charge le modèle LightGBM                              │
  │       │  4. Calcule la prédiction                                  │
  │       ↓                                                             │
  │  { "max_displacement_m": 0.00042, "max_von_mises_pa": 125000000 }  │
  └─────────────────────────────────────────────────────────────────────┘

┌──────────────────────────┬──────────────────────────────────────────────────┐
│ Fichier                  │ Rôle détaillé                                    │
├──────────────────────────┼──────────────────────────────────────────────────┤
│ src/api/main.py          │ FACTORY DE L'APPLICATION FastAPI.                │
│                          │  Assemble les pièces au démarrage :              │
│                          │                                                  │
│                          │  Lifespan : charge les modèles au démarrage,     │
│                          │  démarre en mode dégradé si le chargement échoue │
│                          │  (l'API répond mais /health dit "degraded")      │
│                          │                                                  │
│                          │  Middleware CORS : autorise les requêtes depuis  │
│                          │  le dashboard Streamlit (:8501) et Swagger UI    │
│                          │                                                  │
│                          │  Monte les 2 routers :                           │
│                          │   ops.router    → /, /health, /version           │
│                          │   predict.router→ /predict                       │
│                          │                                                  │
│                          │  Expose /metrics pour Prometheus                 │
│                          │  (si prometheus-fastapi-instrumentator installé) │
│                          │                                                  │
│                          │  Handler global d'erreurs : toute exception non  │
│                          │  gérée retourne HTTP 500 propre au lieu de crash │
├──────────────────────────┼──────────────────────────────────────────────────┤
│ src/api/dependencies.py  │ GARDE D'AUTHENTIFICATION partagée.               │
│                          │  Factorisée ici pour être réutilisée dans les    │
│                          │  deux routers sans duplication de code.          │
│                          │                                                  │
│                          │  Utilise HTTPBasic (user + mot de passe) :       │
│                          │   API_USERNAME  → lu depuis l'env (défaut: admin)│
│                          │   API_PASSWORD  → lu depuis l'env (défaut: mdp123│
│                          │  secrets.compare_digest → résistant aux attaques │
│                          │  par timing (comparaison constante en temps)     │
│                          │                                                  │
│                          │  → Retourne 401 si les credentials sont mauvais  │
├──────────────────────────┼──────────────────────────────────────────────────┤
│ src/api/routers/ops.py   │ ROUTER OPÉRATIONNEL — endpoints de service :     │
│                          │                                                  │
│                          │  GET /         → Page HTML d'accueil avec        │
│                          │    (no auth)      exemples curl pour les 3 types │
│                          │                   de géométrie (with_hole,        │
│                          │                   without_hole, with_hole_moving) │
│                          │                   + status du modèle chargé      │
│                          │                                                  │
│                          │  GET /health   → Sonde de disponibilité          │
│                          │    (no auth)      {"status": "ok"|"degraded",    │
│                          │                    "model_loaded": true/false,   │
│                          │                    "model_version": "v..."}      │
│                          │                                                  │
│                          │  GET /version  → Versions API + modèle           │
│                          │    (auth)         {"api_version": "1.0.0",       │
│                          │                    "model_version": "v...",      │
│                          │                    "feature_count": 42}          │
├──────────────────────────┼──────────────────────────────────────────────────┤
│ src/api/routers/         │ ROUTER D'INFÉRENCE — le cœur de l'API :          │
│   predict.py             │                                                  │
│                          │  POST /predict  → Prend un PredictionRequest,    │
│                          │    (auth)          appelle engineer_features()   │
│                          │                   pour recalculer les 42 features│
│                          │                   puis les 2 modèles LightGBM   │
│                          │                   → retourne un PredictionResponse│
│                          │                                                  │
│                          │  GESTION D'ERREURS :                             │
│                          │   503 → modèle non chargé                        │
│                          │   422 → feature manquante                        │
│                          │   500 → erreur interne (avec log)                │
│                          │                                                  │
│                          │  LOG de chaque prédiction avec géométrie,        │
│                          │  résultats et temps de réponse en ms             │
├──────────────────────────┼──────────────────────────────────────────────────┤
│ src/api/schemas.py       │ Définit le FORMAT exact des données échangées.   │
│                          │                                                  │
│                          │  PredictionRequest = ce qu'on ENVOIE à l'API     │
│                          │   geometry_type, length_m, height_m,             │
│                          │   young_modulus_pa, poisson_ratio, traction_pa,  │
│                          │   material_category, dimension_category,         │
│                          │   hole_radius_ratio (optionnel), hole_cx/cy_ratio│
│                          │                                                  │
│                          │  PredictionResponse = ce que l'API RETOURNE      │
│                          │   model_version, predictions{}, input_summary{}  │
│                          │                                                  │
│                          │  Pydantic valide automatiquement les types :     │
│                          │  Si on envoie "abc" pour length_m → erreur claire│
├──────────────────────────┼──────────────────────────────────────────────────┤
│ src/api/model_loader.py  │ Charge le bon modèle depuis le registre.          │
│                          │                                                  │
│                          │  Lit latest.txt → trouve le dossier de version  │
│                          │  Charge les 2 fichiers .joblib en mémoire        │
│                          │  Cache le modèle (ne recharge pas à chaque fois) │
└──────────────────────────┴──────────────────────────────────────────────────┘

  SIMULATIONS — GÉNÉRATION DES DONNÉES FEM (src/simulations/)
────────────────────────────────────────────────────────────────────────────────

  COMMENT ON GÉNÈRE LES DONNÉES D'ENTRAÎNEMENT ?
  ┌─────────────────────────────────────────────────────────────────────┐
  │  On fait varier les paramètres (largeur, force, diamètre...)        │
  │  Pour chaque combinaison → simulation FEM → résultats               │
  │                                                                      │
  │  Exemple :                                                           │
  │  largeur=0.1m, force=50kN, trou=0.02m → sim → dépl=0.42mm, σ=125MPa│
  │  largeur=0.15m, force=50kN, trou=0.02m → sim → dépl=0.28mm, ...    │
  │  ... (des centaines / milliers de simulations)                      │
  │                                                                      │
  │  C'est ces données que le ML va apprendre à reproduire.             │
  └─────────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────┬──────────────────────────────────────┐

│                                        │  width, height, thickness,           │
│                                        │  hole_diameter, youngs_modulus,      │
│                                        │  poisson_ratio, applied_force        │
├────────────────────────────────────────┼──────────────────────────────────────┤
│ src/simulations/                       │ Simule une plaque SANS trou.         │
│   traction_plate_without_hole.py       │ Plus simple → sert de référence.     │
│                                        │ La contrainte doit correspondre à     │
│                                        │ σ = F/A (loi de Hooke simple)        │
├────────────────────────────────────────┼──────────────────────────────────────┤

│                                        │ Paramètres supplémentaires :         │
│                                        │  hole_cx_ratio → position X (0-1)   │

  ORGANISATION DU DOSSIER data/ :
  ┌─────────────────────────────────────────────────────────────────────┐
  │  data/                                                               │
  │  ├── raw/                  ← Sorties brutes des simulations FEM     │
  │  │   ├── sim_v1/           ← Plaque avec trou centré                │
  │  │   ├── sim_v1_wide/      ← Mêmes params mais plages + larges      │
  │  │   ├── sim_v1_without_hole/       ← Plaque pleine                 │
  │  │   ├── sim_v1_without_hole_wide/  ← Plaque pleine, + large        │
  │  │   ├── sim_v1_low/                ← Basse fidélité (rapide)       │
  │  │   ├── sim_v1_without_hole_low/   ← Idem sans trou                │
  │  │   ├── sim_v2_moving_hole/        ← Trou mobile                   │
  │  │   ├── sim_v2_moving_hole_wide/   ← Trou mobile, + large          │
  │  │   └── sim_v2_moving_hole_low/    ← Trou mobile, basse fidélité   │
  │  │                                                                   │
  │  ├── processed/            ← Données splitées pour ML               │
  │  │   ├── train.parquet     ← 70% des données (apprentissage)        │
  │  │   ├── val.parquet       ← 15% (ajustement hyperparamètres)       │
  │  │   └── test.parquet      ← 15% (évaluation finale, ne pas toucher)│
  │  │                                                                   │
  │  └── features/             ← Données avec features engineered       │
  │      └── advanced/                                                   │
  │          ├── features.parquet      ← Tout dataset, 42 features      │
  │          └── feature_columns.txt   ← Liste des 42 noms de colonnes  │
  └─────────────────────────────────────────────────────────────────────┘

  POURQUOI 3 NIVEAUX (raw / processed / features) ?
  ┌─────────────────────────────────────────────────────────────────────┐
  │                                                                      │
  │  raw/      → Données originales des simulations (JAMAIS modifier)   │
  │     ↓         (CSV avec les colonnes de base : width, force, etc.)  │
  │  processed/→ Données nettoyées + splitées en train/val/test         │
  │     ↓         (format Parquet = plus rapide que CSV)                 │
  │  features/ → Données enrichies avec les 42 features physiques        │
  │               C'est CE DOSSIER que le modèle ML lit pour apprendre  │
  │                                                                      │
  └─────────────────────────────────────────────────────────────────────┘

  NIVEAUX DE FIDÉLITÉ DES SIMULATIONS :
  ┌──────────────────┬────────────────────────────────────────────────┐
  │ Suffixe          │ Signification                                  │
  ├──────────────────┼────────────────────────────────────────────────┤
  │ (rien)           │ Fidélité standard — maillage moyen             │
  │ _wide            │ Mêmes paramètres mais plages de valeurs plus   │
  │                  │ larges → le modèle généralise mieux            │
  │ _low             │ Basse fidélité → maillage plus grossier →      │
  │                  │ simulation rapide mais moins précise            │
  └──────────────────┴────────────────────────────────────────────────┘

  FORMAT PARQUET vs CSV :
  ┌──────────────────────────┬──────────────────────────────────────────┐
  │ CSV                      │ Parquet                                  │
  ├──────────────────────────┼──────────────────────────────────────────┤
  │ Lisible par humains      │ Binaire compressé                        │
  │ Lent à lire (pandas)     │ 10-50x plus rapide en lecture            │
  │ Prend beaucoup de place  │ 5-10x plus petit                         │
  │ → pour les raw           │ → pour processed et features             │
  └──────────────────────────┴──────────────────────────────────────────┘

  FLUX DE LA CI :
  ┌───────────────────────────────────────────────────────────────────┐
  │  git push main                                                     │

  │       ↓                                                            │

  │       ↓                                                            │
  │  Lint : py_compile (vérifie la syntaxe de tous les modules)       │
  │       ↓                                                            │
  │  Tests : python -m unittest discover tests/                       │
  │       ↓                              ↓                            │
  │  Succès → Slack ✅              Échec → Slack ❌                   │
  └───────────────────────────────────────────────────────────────────┘
